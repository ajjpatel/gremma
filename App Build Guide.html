Companion to the Hackathon Plan · Gemma 4 + LiteRT-LM · Android & iOS

How to build the app, step by step

The engineering companion to the plan: exactly what to install, what to download, what you can use as-is with zero setup, what you embed as an SDK, and the order to build each feature in. Written for tomorrow — every step is something the team can actually finish in a day.

THE SHORT ANSWER TO “DO WE SET UP LOCALLY, OR USE SOMETHING DIRECTLY?”

Both, in layers. You use three things directly, with no conversion work at all: the AI Edge Gallery app (runs Gemma 4 on both phones in minutes — your safety net), the LiteRT-LM desktop CLI on the Mac (test prompts from a terminal before writing app code), and pre-built .litertlm model files from Google’s litert-community org on Hugging Face. Your own code is a thin native shell — Kotlin on Android, Swift on iOS — that loads those files through the LiteRT-LM SDK. You do not convert or train any model for this hackathon. Model conversion exists (Door 3 below) and is a post-hackathon topic.

01Three doors — pick per job, not per project

Everything in this guide is one of three moves. The tabs below spell out what each door involves, what it costs in time, and which parts of the app use it. Most teams only ever open Doors 1 and 2.

USE FOR: TONIGHT + DEMO FALLBACK · SETUP: ~15 MIN

No code. Google ships two ready-made runners.

AI Edge Gallery (free, by Google, on both app stores) downloads Gemma 4 onto the phone and runs it fully on-device — chat, image input, and a Prompt Lab where you paste a system prompt and test it. No account, nothing leaves the phone. This is how you validate every prompt tonight, and it is the fallback demo if the team’s own build breaks in front of judges.

LiteRT-LM CLI on the Mac does the same job from a terminal: import a model once, then chat with it, script it, and diff prompt versions quickly — far faster iteration than rebuilding a phone app for every wording change. Prompts that pass on the CLI get pasted into the app unchanged.

What Door 1 cannot do: your camera pipeline, your voice shell, your Find database. Anything user-facing beyond a chat window needs Door 2.

USE FOR: THE ACTUAL APP · SETUP: ~1 HOUR PER PLATFORM

Embed LiteRT-LM in a native app. This is the real build.

LiteRT-LM is Google’s production runtime for language models (the successor to the MediaPipe LLM Inference API, which is now maintenance-only — do not start new code on it). It ships as a normal library: a Gradle dependency on Android, a Swift package on iOS. The API surface is deliberately tiny: an Engine loads a .litertlm file, a Conversation holds the chat, and replies stream back token by token.

Your app around it is ordinary native code: camera frames in, streamed text out to text-to-speech. The same model files, the same prompts, and the same data design run on both platforms — that is the honest version of “one system, two apps.”

Flutter note: a community litertlm package exposes the same Engine/Conversation API in Dart, and the plan’s shared-UI idea can ride on it. But ARKit/ARCore depth and background processing still need native modules on each side, so Flutter saves UI code, not platform code. For a one-day build with two phone owners, native + native is the lower-risk split.

USE FOR: AFTER THE HACKATHON · SETUP: HALF A DAY + GPU TIME

Convert or fine-tune your own model into .litertlm.

If you ever fine-tune Gemma (say, on accessibility narration examples), the checkpoint has to be exported to LiteRT format with litert-torch and quantized before a phone can load it. That pipeline lives in section 12. It is real work with real traps, and none of it is needed tomorrow: Google’s stock instruction-tuned builds already do everything the demo asks of them. Skip this door until the trophy is home.

02The stack — what runs where

Four kinds of software, each doing only the job it is fast enough for. This is the three-tier design from the plan, expressed as components you actually install.

VOICE SHELL

Platform speech APIs — no model download. iOS: Speech framework (on-device recognition) + AVSpeechSynthesizer. Android: SpeechRecognizer + TextToSpeech. Free, offline, instant. Gemma never does speech.

↓ spoken command · camera frames ↓
TIER 0 · ALWAYS ON

LiteRT vision model + depth. A MediaPipe Tasks object detector (EfficientDet-Lite class, a few MB, <50 ms/frame) watches every frame; ARKit scene depth (LiDAR, iPhone) or ARCore Depth API (Pixel) gives distance. Frame-differencing decides whether anything changed. Costs almost nothing.

↓ only when the scene changes, or the user asks ↓
TIER 1 · ON DEMAND

Gemma 4 via LiteRT-LM. E4B (3.65 GB) on the iPhone 16 Pro Max; E2B (2.58 GB) on a 12 GB Pixel. Narrates scenes, reads labels, answers questions. Called rarely by design — that is the whole compute strategy.

↓ captions in · queries in ↓
MEMORY · FIND

EmbeddingGemma + SQLite. EmbeddingGemma (308M; text-only config runs in ~200 MB RAM) turns Gemma’s captions into vectors stored in a plain SQLite table on the phone. “Where are my keys?” is a cosine-similarity lookup, not a model call.

04Set up the Mac — tonight, in this order

One Mac builds both apps. The order matters because Xcode is the long pole: start its download first and install everything else while it runs. The full file list is section 3; this is the sequence.

Check the disk, then start Xcode downloading

Confirm 50 GB free. Xcode needs roughly 45–50 GB of working room between the compressed download and the unpacked app. Start the Mac App Store download now — on venue Wi-Fi tomorrow this step alone would eat the morning.

Command Line Tools, Homebrew, Python

TERMINAL

xcode-select --install
# Homebrew (from brew.sh), then:
brew install python@3.12 uv git
python3 --version && uv --version

uv manages the Python tools (LiteRT-LM CLI, later litert-torch) without polluting the system Python.

Android Studio + SDK

Install Android Studio, open it once, and let it download the SDK and platform tools. Confirm adb works — you will use it to push model files to the Pixel over USB:

adb version
adb shell getprop ro.soc.model   # later, with the Pixel plugged in — tells you which model variant it wants

Hugging Face account + Gemma license

Create a free Hugging Face account and accept the Gemma license on the model pages tonight — the litert-community downloads are gated, and a license click is a stupid thing to be blocked on at 10 AM. Then log the CLI in:

uvx huggingface_hub login   # paste your HF access token when asked

Download the model files to the Mac as backup

Keep local copies of the E2B and E4B .litertlm files (~6.2 GB total). If venue Wi-Fi dies, models reach the Pixel over USB (adb push) and the iPhone through Finder/Xcode device storage. Files are listed in section 8.

Open Xcode once and finish its first-run setup

Accept the license, let it install components and an iOS simulator runtime, and plug in the iPhone to pair it (trust prompt on the phone). A first launch at the venue burns 20 minutes you don’t have.

05Prove the model on the Mac CLI — before any app code

Thirty minutes here saves hours later: if Gemma answers your prompts well in a terminal, the phone work is “just” plumbing. If it doesn’t, you fix wording — on the machine where iteration takes seconds.

Install the LiteRT-LM CLI

python3 -m venv ~/.litert-env
source ~/.litert-env/bin/activate
pip install litert-lm

Or skip the install for a one-off chat: uvx litert-lm chat google/gemma-4-e2b-it downloads and runs the E2B in one line.

Import the model

litert-lm import \
  --model-id litert-community/gemma-4-E2B-it-litert-lm \
  --output-dir ~/.litert-lm/models/gemma4-e2b/

This pulls the same .litertlm file the phones will run. On Apple Silicon the CLI uses the Metal GPU backend automatically, so speeds are in the same family as the phones.

Run the prompt test battery

litert-lm run --model-path ~/.litert-lm/models/gemma4-e2b/model.litertlm

Feed it the team’s test set: the narrator prompt on described scenes, the Read prompts on typed-out label text, and — critically — the ambiguous cases where the correct answer is “I can’t tell.” Score it against the trust scorecard from the plan page. Lock the winning wording in a shared prompts.md; both apps paste from that file, never from memory.

RULE OF THUMB

Temperature ~0.2–0.3 for Read and Find (factual — you want the boring answer), up to ~0.7 for Visualize (descriptive — you want some life in it). Cap narration at ~120 output tokens: at ~25 tokens/sec on the phone, that is the difference between a 3-second answer and a 10-second one.

06Build the Android app (Kotlin)

The Pixel is the flagship demo device, so Android goes first. Target: a skeleton that loads Gemma and answers one question within the first hour.

New project, one dependency

Empty Activity project in Android Studio (Kotlin, Jetpack Compose is fine but not required). Add LiteRT-LM from Google Maven to the app module:

APP-LEVEL build.gradle.kts

dependencies {
    implementation("com.google.ai.edge.litertlm:litertlm-android:0.18.0")
}

That one line is the whole runtime. No native build, no Bazel, no NDK work — building LiteRT-LM from source is only for people patching the runtime itself.

Get the model file onto the device as a real file

LiteRT-LM needs a filesystem path — it cannot read a model out of the APK assets directly, and a 2.6 GB file doesn’t belong in an APK anyway. For the hackathon, push the Mac backup over USB into app storage; for a shipped app, download on first launch instead (see section 8).

adb push gemma-4-E2B-it.litertlm /data/local/tmp/
# then copy it into the app's files dir from your setup screen,
# or point the Engine at a path your app can read.

Create the Engine — once, at app start, off the UI thread

val engine = Engine(EngineConfig(
    modelPath = modelFile.absolutePath,
    backend = Backend.GPU(),          // fall back to Backend.CPU() if init fails
    cacheDir = context.cacheDir.path  // speeds up every later load
))
engine.initialize()  // can take up to ~10 s — background coroutine, never per request

Keep this Engine alive for the whole app session. Creating and destroying it per question is the single most common cause of “on-device AI is slow” demos.

Open a Conversation with the safety system prompt

val conversation = engine.createConversation(ConversationConfig(
    systemInstruction = Contents.of(SAFETY_SYSTEM_PROMPT),  // from prompts.md
    samplerConfig = SamplerConfig(topK = 40, topP = 0.95, temperature = 0.3)
))

One Conversation per mode (Narrate, Read, Find, Visualize), each with its own system prompt from prompts.md. Switching mode = switching conversation, not reloading the model.

Send a camera frame, stream the answer into TTS

conversation.sendMessageAsync(
    Message.of(imagePart, textPart)   // frame + "What changed since: <last summary>?"
).collect { partial ->
    // stream tokens: buffer to sentence boundaries,
    // hand each finished sentence to TextToSpeech
}

sendMessageAsync returns a Kotlin Flow of partial replies. Speaking sentence-by-sentence instead of waiting for the full reply cuts perceived latency to roughly the first-token time (~1 s).

Wire the rest

CameraX for frames, SpeechRecognizer for commands, ARCore for the depth session, WorkManager (charging constraint) for background video indexing. Each is a standard Android library — no AI-specific surprises left once the Engine works.

07Build the iOS app (Swift)

Same architecture, Apple-shaped pieces. LiteRT-LM now ships an official open-source Swift API with a Metal GPU backend, so Gemma runs the same way as on Android — same .litertlm files, same prompts.

New SwiftUI app, add the LiteRT-LM Swift package

In Xcode: File → Add Package Dependencies, and add the LiteRT-LM Swift package from Google’s LiteRT-LM repository. (A community wrapper, swift-litert-lm on GitHub, packages the same runtime with a chat UI and in-app model download — a legitimate shortcut if the official package fights you at 11 AM.)

Download the model on first launch — never bundle it

The app binary stays small; on first launch it downloads gemma-4-E4B-it.litertlm (3.65 GB) from the litert-community Hugging Face repo into Application Support, marked excluded from iCloud backup, and reuses it forever after. Tonight, pre-download it over home Wi-Fi so tomorrow’s “first launch” is instant — or side-load the Mac backup through Xcode’s device storage.

Load the engine, open a conversation, stream

The Swift API mirrors the Kotlin one: engine from a model file URL, conversation with a system instruction, streamed responses. Load once at app start on a background task; speak the reply via AVSpeechSynthesizer as sentences complete — identical pattern to Android step 5.

Test on the physical iPhone — the simulator lies

The Metal GPU backend only engages in a signed app on a real device; the iOS Simulator silently falls back to CPU and everything looks 5–10× slower than reality. All performance judgements happen on the 16 Pro Max, never the simulator.

Wire the Apple pieces

AVFoundation for camera, ARKit for LiDAR scene depth, Speech framework with on-device recognition for commands, Core Haptics for directional hazard taps, BGProcessingTask (runs while charging) for overnight video indexing.

TEAM REALITY CHECK

Two native apps is two codebases. If the team is three people, not four, the honest cut is: build Android properly (loaner Pixel = flagship tracks), and run the iPhone demo through AI Edge Gallery + your locked prompts. A working Gallery demo on iOS beats a half-built Swift app on both.

THE VARIANT TRAP

SoC-specific builds are not interchangeable. An NPU-compiled file (Tensor, Snapdragon) embeds compiled ops for that one chip — load it on the wrong backend and it crashes; the generic GPU build cannot use the NPU either. Rule for tomorrow: ship the generic GPU build everywhere. Only touch a chip-specific file with that exact phone in your hand and an hour to spare. Check a Pixel’s chip with adb shell getprop ro.soc.model.

09The shared pieces — build each feature from the same parts

Nothing here is platform-specific in design — only in API names. Build each piece once per platform, in this dependency order.

Piece 1 · Voice shell

One big invisible talk button (press-and-hold) plus spoken menus. Speech-to-text and text-to-speech come from the OS (section 2) — your code is a state machine: listen → match command → run mode → speak result → listen again. Every screen must be reachable and readable through this loop alone; the visual UI is a debugging aid for sighted teammates.

Piece 2 · Camera + delta gate

Grab frames at ~2 fps. Downscale each to a small grayscale thumbnail and diff it against the last kept frame; also sample the depth map’s center region. Three outcomes:

  • Nothing changed → throw the frame away. No detector run, no Gemma call. This is where the 80–90% compute saving physically happens.
  • Pixels changed, no near obstacle → run the Tier-0 detector; if the object set changed, escalate to Gemma with “previous summary + what changed?”.
  • Depth says something is close and in-path → hazard path: haptic pulse (side = direction) and a short spoken warning from the detector + depth only. Gemma is never in this path — it is too slow and can invent things.

Piece 3 · The narration call

One function, used by Narrate and Read: frame + mode prompt → streamed reply → TTS by sentence. Read mode is the same call with a stricter prompt (“Read exactly the text you can see. If a word is unreadable, say so — never guess a dosage, date, or amount.”) and temperature 0.2.

Piece 4 · Find — the indexing pipeline

Record

User walks the room filming (or imports a video). Store the video in app storage; indexing can happen later, while charging.

Extract keyframes — reuse the delta gate

Sample the video at 1 fps and keep only frames that differ meaningfully from the last kept one. A 3-minute room tour typically collapses to a few dozen frames.

Caption each keyframe with Gemma

Structured prompt, structured answer: room guess, items visible, and each item’s position relative to landmarks (“keys — kitchen counter, left of the stove”). Ask for JSON; validate before storing; on invalid JSON, retry once, then store the raw text.

Embed and store

Run the caption text through EmbeddingGemma and insert one SQLite row per item:

items(
  id INTEGER PRIMARY KEY,
  name TEXT,            -- "keys"
  room TEXT,            -- "kitchen"
  location_text TEXT,   -- "counter, left of the stove"
  embedding BLOB,       -- 768-dim float vector from EmbeddingGemma
  video_id INTEGER, ts INTEGER
)

Answer queries by lookup, not generation

“Where are my keys?” → embed the query → cosine similarity over the table (a few hundred rows is instant, no vector database needed) → speak the stored location_text verbatim. Gemma may polish the sentence, but the facts come from the row — this is what keeps Find honest.

Piece 5 · Visualize

No camera, no retrieval: a Gemma conversation seeded with the verified facts file for each demo monument (loaded as context text) and a fixed descriptive structure — overall scale in familiar comparisons, layout, then a slow mental walk-through. Facts from the file, colour from the model.

10Build order for hackathon day

Sequenced so that at every hour mark, something demonstrable exists. If the day goes sideways, stop anywhere on this list and you still have a demo.

Hour 0–1 · Both phones proven

Gallery installed, model downloads started on the loaner Pixel immediately (see the downloads checklist), prompts from prompts.md passing the CLI battery on the Mac. Android skeleton created, LiteRT-LM dependency in, Engine loads on the Pixel with a hardcoded “hello” — the riskiest unknown dies first.

Hour 1–2 · Hear it speak

Camera frame → Gemma → streamed TTS. Voice command in via platform speech. You now have Narrate end-to-end on Android, however ugly.

Hour 2–3 · Read mode + safety pass

Read conversation (medicine label, expiry, currency) with the strict prompt; run the trust scorecard; fix every invented answer by tightening wording, not code. iOS dev mirrors the same flow (or prepares the Gallery demo if the team is three).

Hour 3–4 · Find, one room

Record the demo room, run the indexing pipeline, store ~10 items, voice-query them. This is the feature judges remember — protect this hour.

Hour 4–5 · Delta gate + hazard awareness

Frame-differencing in front of the narration call (count Gemma calls on screen — that counter is a pitch asset), detector + depth hazard path with haptics, honestly labelled assistive-not-navigation.

Hour 5–6 · Visualize + polish

Two monuments from verified facts. Then: airplane-mode rehearsal of the full 90-second script, twice, on both phones. Freeze features.

Final hour · Demo hardening

Charge everything, kill notifications, pre-load every conversation, rehearse the fallback (Gallery) switch. Nobody debugs live in front of judges.

11Gotchas — the ones that actually bite

  • Engine init takes up to ~10 seconds. Load once at app start on a background thread, speak a “warming up” state, and keep the Engine resident. Per-request init is the classic demo-killer.
  • LiteRT-LM is pre-1.0 (0.18.x). The API is small and stable enough to build on, but pin the exact version in Gradle/SPM and don’t upgrade mid-hackathon.
  • MediaPipe’s LLM Inference API is maintenance-only. Old tutorials point at it; Google now puts new work into LiteRT-LM. MediaPipe Tasks is still the right tool for the detector and embedder — only the LLM piece moved.
  • Wrong SoC variant = crash, not slowdown. Generic GPU build unless you are deliberately doing the NPU experiment (section 8).
  • The simulator has no Metal GPU path. iOS performance testing happens on the physical iPhone only.
  • Models need real file paths. Not APK assets, not Flutter assets, not bundle resources — a file in app storage with a path the Engine can open.
  • Background indexing is OS-rationed. iOS BGProcessingTask and Android WorkManager both prefer charging + idle. Design Find so indexing is resumable and the demo room is indexed manually, in the foreground, on the day.
  • Long answers are slow answers. Token caps per mode (section 5) are a performance feature, not an editing preference. Stream to TTS by sentence.
  • Thermal reality. Sustained back-to-back Gemma calls throttle both phones. The delta gate isn’t an optimization — it’s what makes the app survivable. Show the call counter in the demo.

12Door 3 in detail — converting your own model (post-hackathon)

Only for a fine-tuned or non-stock model. Stock Gemma builds never need this — they are published pre-converted, which is precisely why the hackathon build is feasible in a day.

Fine-tune or pick a checkpoint on Hugging Face

Work in PyTorch/HF format on the Mac (or a rented GPU for anything serious). Keep the base model’s tokenizer — the runtime expects it.

Export with litert-torch

uv tool install litert-torch-nightly
litert-torch export_hf \
  --model your-org/your-finetuned-gemma \
  --output ./out/model.litertlm   // + int4/int8 quantization flags to fit phone RAM

Quantization is not optional garnish: an unquantized build is several times larger and simply won’t fit the phone memory budget alongside the OS and your app.

Validate on the CLI before touching a phone

Run the exact trust-scorecard battery from section 5 against the exported file. Conversion bugs show up as quality bugs, not errors.

THE CHAT-TEMPLATE TRAP

A known failure: exporting bundles the Hugging Face Jinja chat template, whose functions LiteRT-LM’s on-device template parser doesn’t support. The model loads, the tokenizer initializes, nothing crashes — and inference quietly produces garbage. If a converted model “works but talks nonsense,” suspect the template first and swap in a known-compatible one before re-exporting.
